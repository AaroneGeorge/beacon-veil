### Project Summary

We are not redesigning the light client. It runs the Helios light-client rules from `a16z/helios` 0.12.0, unmodified, inside a RISC Zero 3.0.5 guest, on LEZ v0.4.0-rc3. Helios is open source, maintained by a16z since 2022, and is the core of SP1 Helios and R0VM Helios. It is not audited by itself: its README says so, and the audits of those two products treated it as a dependency (section 4). The bridge in our RFP-022 proposal consumes this primitive. We deviate from the RFP's expected design in one place: the unmodified Helios library does not fit the 10,000,000 gas transaction cap, so verification runs on a privately proven path first, and the public path is measured beside it.

Platform risk. LEZ v0.4.0-rc3 pins `risc0-zkvm` 3.0.5, which is affected by RISC Zero advisory GHSA-g6qg-9j8p-7j87 (critical, published 2026-11-11, fixed in 3.1.0). Our LEZ-side code moves to 3.1.0 when LEZ does.

This proposal and our RFP-022 proposal are one project, filed as two issues. The combined price is $88,000 for about 20 calendar weeks. The RFP-021 share is $32,000. The audit is a separate allowance that Logos contracts and pays. It is not in the $88,000.

#### 2. The measurement behind the design (P1, P2, P8)

The RFP calls in-program BLS12-381 verification the central feasibility question. We ran the unmodified library on five real mainnet updates (RISC Zero 3.0.5 executor, dev mode, Intel i5-10300H; generated by `make cost-exec` on 2026-11-12 20:20 UTC from the reproducible guest set; raw: `evidence/cost/raw/exec-lc.json`, table: `evidence/cost/cost.md`). In every step the executor's output equals the native result.

| Update | Bytes | Signers of 512 | User cycles | Cycles divided by the 10M cap |
|---|---|---|---|---|
| Period 1905, learns next committee | 26,914 | 511 | 61,174,483 | 6.1 |
| Period 1906, handoff | 26,926 | 512 | 64,333,601 | 6.4 |
| Period 1907, handoff | 26,920 | 511 | 65,461,983 | 6.5 |
| Period 1908, handoff | 26,922 | 512 | 64,332,682 | 6.4 |
| Finality update | 2,109 | 512 | 46,095,505 | 4.6 |

With unmodified Helios one update is 4.6 to 6.5 times the per-transaction cap, so it cannot run in one public transaction. We sent the same `Verify` as a public transaction on the sequencer: the wallet refuses it in simulation ("Execution exceeded its cycle budget of 10000000 cycles"), and when forced it is included and reverted (tx `43902552...c38d`, block 334, instance head unchanged; raw: `b0-public-verify-2026-11-12.log`, TODO-REFRESH: copy into `evidence/cost/raw/`). Other applicants report 11.2 million to 14.6 million cycles for hand-written updates (rfp#224 and rfp#247; their figures, not ours).

Where the cycles go, on the finality update with 512 signers, measured by running the same `bls12_381` calls a second time on the same inputs (`evidence/cost/raw/w1-v1-trace.log`): signature subgroup check 8,767,621; Miller loop with two pairs 9,856,680; final exponentiation 12,383,570; hash-to-curve 3,083,859; signature decompression 1,599,037; key aggregation 1,150,440. The BLS phases sum to 36.84 million of the 37.33 million cycles of Helios `verify` and `apply`. The remainder of the 46.1 million is our glue: the committee root hash, the witness and the commitments.

Three variants, same interface. V1 is Helios unmodified (above). V2 is the Helios rules with one function replaced: Helios decompresses the signature, which already rejects points outside the subgroup, and then runs the subgroup check again. V2 drops the repeat. V2 costs 37,032,744 cycles on the finality update and 45.6 million to 49.9 million on the period updates (`evidence/cost/cost.md`). A differential test gives V1 and V2 the same result or the same error code on the real chain and on 165 tampered updates. V2 is not unmodified Helios, so it adds a short function to the audit surface. V3, a hand-written pipeline, is not built. The consequence for operators is in section 10.

#### 3. Architecture (F1, F9, F13 to F15, S1)

Two programs. `attest` is small and long-lived: the instance state, `Init`, `Apply`, write-once header records, `CheckHeader` and `Attest`. `lc_verify` is replaceable per Ethereum fork: it runs Helios verification and application and nothing else, and is deployed immutable. An instance's config lists the verifier program ids it accepts. The instance address is the PDA of the config hash, so the checkpoint, chain id, forks and verifier set cannot change after initialisation (F9, F13). A new fork means a new verifier and a new instance under the same `attest` program id. Two programs because the deployed-ELF cap of 1,966,080 bytes does not allow Helios and the instance logic in one.

Path A, in the prototype: `Verify` runs in a private actor of `lc_verify`. The privacy circuit composes its receipt, so the 10M cap does not apply to it. It sends a sync message `Apply` to the public instance actor. `Apply` checks that the sender's program id is in the config and that the pre-state commitment equals the stored one. On chain the update costs 409,764 gas for receipt verification (`PRIVATE_VERIFY_GAS`), 54,965 cycles for `Apply` and 24,047 for `WriteRecord` (measured), which is 488,776 execution gas, 4.9 percent of the 10M cap. It also costs 224,063 storage gas (`PRIVATE_GAS_STOR`), 22.4 percent of a block's storage gas. The constants are in `market.rs`, read in the pinned tree on 2026-11-12, and the source marks them provisional. The sums are derived in `evidence/cost/cost.md` section 2.

Path B, public, sequencer-executed: a second verifier id in the same config. B0 is measured (section 2): the monolithic `Verify` is 4.6 to 6.5 times the cap. If the work splits into perfectly even phases with no overhead, it needs at least 5 to 7 transactions (estimate, `evidence/cost/cost.md` section 3). In M1, if Logos asks for it, we build the split over several public transactions ending in the same `Apply` (B1). When LEZ gets a BLS12-381 precompile, B becomes one transaction and nothing else changes. This keeps the RFP's expectation that tracking can live on the public path, and it gives our own numbers for P8.

Source facts behind Path A, from the LEZ rc3 source read during research on 2026-11-11: the privacy circuit verifies the program's receipt with `env::verify` and does not re-run it, so the cap does not apply (`lee/privacy_preserving_circuit/src/private_backend.rs:60-80`); a private sender's program id carries over, so `Apply` can check who sent it (`execution_state.rs:1409-1428`); the sequencer checks the private run against the deployed program image (`validated_state_diff/mod.rs:655-683`); and LEZ's own `wrapped_token`, `bridge_lock` and `cross_zone_inbox` gate handlers on `from_own_program()`. Our chain test confirms the sender check (`evidence/g1/chain.json`).

Costs of Path A, stated: proving moves to the submitter's hardware; each private update takes one of about four private-transaction slots in a block (storage gas is capped at 1,000,000 per block and a private transaction is charged 224,063, our arithmetic from `market.rs`); it departs from the RFP's statement that tracking belongs on the public path (lines 366 to 373 of the RFP). We ask Logos at M0 to confirm that both paths, measured, meet the intent.

#### 5. Inclusion, predicates, statement identifier, chain binding (F3 to F6)

- Claims. An account, a storage slot or a receipt log, each with its Merkle-Patricia proof, verified under the roots of a header record. The caller never supplies a root. Tests run on real mainnet and Sepolia proofs, including tampered nodes, a proof for another key and swapped account proofs.
- Gloas. A gloas light-client header carries only the execution block hash. The record keeps that hash and a claim carries the RLP execution header, which must hash to it. `docs/TRUST.md` section 3 shows why this is sound under the current spec.
- Predicates. `Eq`, `Ne`, `Lt`, `Le`, `Gt`, `Ge` over u256 or bytes32, `LogTopicEq`, `LogDataWordEq` and `All`. A consumer passes a predicate without changing the module. A predicate that names a field the claim does not carry is rejected with E10.
- Statement id. For a log: `sha256("esa/stmt/v1" || chain_id || exec_hash || tx_index || log_index || keccak(log))`. For an account or storage fact: `sha256("esa/stmt/v1" || chain_id || address || slot_key || value)`. Identical state gives an identical id.
- Chain binding. Every statement carries the chain id and instance. A consumer rejects a mismatch with E09. Test: `vs2e_wrong_chain_id`. TODO-TEST: the same contract address on mainnet and Sepolia.

#### 6. Consumption model and privacy (F7, F8, R2, R11)

`Attest` is a handler, so one verification core serves both placements. On a public account it runs metered. On the user's private account it is proven on the user's device and discloses only which shared header record it read. Header records are public, write-once accounts. Private consumers read them and never write them, so they do not contend in a block (R11). The consumer owns uniqueness. The reference consumer keys its nullifier on the statement id and its own instance (section 11). A rejected attestation consumes nothing (R2). #### 7. Permissionless operation (F11, F12, R7 to R10)

Anyone can submit a valid update. `Apply` accepts any `Verify` from a verifier listed in the config and checks nothing about the submitter. A test submits an update from a private account created seconds earlier.

| Off-chain participant | Safety or liveness | Why it cannot block |
|---|---|---|
| Update submitter | Liveness only | Any other party submits the same update. A stalled instance resumes by submitting the outstanding updates in order |
| Beacon API provider | Liveness only | The follower fails over across providers. A bad update is rejected by the program |
| Execution RPC provider | Liveness only | Another provider serves the same proof. A bad proof is rejected |
| Claimant's prover | Neither | It is the user's own device |

The follower reads the on-chain head, waits an interval derived from `sha256(instance || follower_id || slot)` in 0 to `jitter_max_s` (default 60 s), reads the head again, and submits only if the update is still needed (R9, R10). A duplicate is rejected with E14 (R8). A restarted follower checks its local store against the on-chain commitment and resumes without re-verifying from the checkpoint (R4). The default cadence is one finality update every 6,144 s, and a handoff goes at once. `docs/OPERATOR.md` has the operator journey. No party is obliged to operate. #### 11. Trust assumptions and verification security (S6, VS1 to VS6)

Full text: `docs/TRUST.md`.

- Sync committee. We trust that fewer than 342 of 512 members collude. If an attacker holds a fraction f of the effective stake, the chance of at least 342 of 512 seats in one period is a binomial tail. At f = 0.5 it is 1.2e-14, at 0.6 it is 8.9e-4, at 0.65 it is 0.21 (computed, not measured). The cheaper attack corrupts the keys of 342 known seats in the 27 hours before a period starts, and costs the attacker no stake because the spec has no slashing for sync-committee signing. This is weaker than Ethereum's economic finality. We state it and do not offer a stronger anchor.
- Checkpoint. One trust input, checked by comparing public sources. A wrong one is fixed by a new instance.
- Gloas. The header attests the bid's parent block hash (generalized index 2,856, consensus-specs `c3e16117`). A payload that was withheld cannot reach a finalised header. A gloas record lags by one or more slots.
- Helios is not audited by itself. We say so in section 4 and budget for the auditor to read the functions we call. The part of the trust story that holds is that we run unmodified upstream code that others depend on, instead of rules we wrote.
- RISC Zero advisory GHSA-g6qg-9j8p-7j87 (critical, 2026-11-11): an attacker who can produce one valid Groth16 receipt can have an arbitrary claim accepted. It affects `risc0-zkvm` below 3.1.0 and Groth16 verifier 3.0.0. LEZ v0.4.0-rc3 pins 3.0.5. Until LEZ moves to 3.1.0, receipt checks on LEZ rest on an affected version. This is a platform risk we cannot remove, and we move our LEZ-side code with LEZ.
- Helios quorum finding. Helios `verify_generic_update` does not enforce the two-thirds quorum and treats a zero finalized header as no finality. `lc_verify` therefore checks decode (E01), finalized header present (E02) and participants of at least `max(min_participants, 342)` (E04) before Helios, and that the store moved (E14) after. Tests `vs2b_below_participation` and `vs2c_header_not_finalised`.
- Nullifier keying. The consumer nullifier is `PDA(program, sha256(domain || program_instance || stmt.id))`. Without the instance in the seed, an attacker's instance can accept a fabricated statement with the id of a real transfer and burn it for good.
- Adversarial suite. `vs1_fabricated_chain`, `vs2a_committee_not_handed_off`, `vs2b_below_participation`, `vs2c_header_not_finalised`, `vs2d_tampered_roots`, `vs2e_wrong_chain_id`, `vs2f_predicate_not_covered`. Each asserts an exact error code.
- Immutability (VS3). `lc_verify` is deployed immutable. Verifier ids are part of the config that fixes the instance address. A fix or a new fork means a new instance, and consumers move as in `docs/CONSUMER-PATTERN.md` section 7. The consumer document states that a program holding our program id in mutable state hands control to whoever writes that state.
- Failure modes and consumer exposure (VS4). Caps, a freeze authority, a delay before large releases, an out-of-band check of large amounts. `docs/TRUST.md` section 5.
