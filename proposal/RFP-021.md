#### 3. Architecture (F1, F9, F13 to F15, S1)

Two programs. `attest` is small and long-lived: the instance state, `Init`, `Apply`, write-once header records, `CheckHeader` and `Attest`. `lc_verify` is replaceable per Ethereum fork: it runs Helios verification and application and nothing else, and is deployed immutable. An instance's config lists the verifier program ids it accepts. The instance address is the PDA of the config hash, so the checkpoint, chain id, forks and verifier set cannot change after initialisation (F9, F13). A new fork means a new verifier and a new instance under the same `attest` program id. Two programs because the deployed-ELF cap of 1,966,080 bytes does not allow Helios and the instance logic in one.

Path A, in the prototype: `Verify` runs in a private actor of `lc_verify`. The privacy circuit composes its receipt, so the 10M cap does not apply to it. It sends a sync message `Apply` to the public instance actor. `Apply` checks that the sender's program id is in the config and that the pre-state commitment equals the stored one. On chain the update costs a flat 409,764 gas for receipt verification, the cycles of `Apply`, and 224,063 storage gas (`PRIVATE_VERIFY_GAS` and `PRIVATE_GAS_STOR` in `market.rs`, read in the pinned tree on 2026-11-12; the source marks them provisional; TODO-MEASURE on our own run).

Path B, public, sequencer-executed: a second verifier id in the same config. In the prototype we run the monolithic `Verify` in the public executor and record cycles per phase (B0, TODO-MEASURE). In M1, if Logos asks for it, we split the work over three or more public transactions ending in the same `Apply` (B1). When LEZ gets a BLS12-381 precompile, B becomes one transaction and nothing else changes. This keeps the RFP's expectation that tracking can live on the public path, and it gives our own numbers for P8.

#### 5. Inclusion, predicates, statement identifier, chain binding (F3 to F6)

- Claims. An account, a storage slot or a receipt log, each with its Merkle-Patricia proof, verified under the roots of a header record. The caller never supplies a root. Tests run on real mainnet and Sepolia proofs, including tampered nodes, a proof for another key and swapped account proofs.
- Gloas. A gloas light-client header carries only the execution block hash. The record keeps that hash and a claim carries the RLP execution header, which must hash to it. `docs/TRUST.md` section 3 shows why this is sound under the current spec.
- Predicates. `Eq`, `Ne`, `Lt`, `Le`, `Gt`, `Ge` over u256 or bytes32, `LogTopicEq`, `LogDataWordEq` and `All`. A consumer passes a predicate without changing the module. A predicate that names a field the claim does not carry is rejected with E10.
- Statement id. For a log: `sha256("esa/stmt/v1" || chain_id || exec_hash || tx_index || log_index || keccak(log))`. For an account or storage fact: `sha256("esa/stmt/v1" || chain_id || address || slot_key || value)`. Identical state gives an identical id.
- Chain binding. Every statement carries the chain id and instance. A consumer rejects a mismatch with E09. Test: `vs2e_wrong_chain_id`. TODO-TEST: the same contract address on mainnet and Sepolia.

#### 6. Consumption model and privacy (F7, F8, R2, R11)

`Attest` is a handler, so one verification core serves both placements. On a public account it runs metered. On the user's private account it is proven on the user's device and discloses only which shared header record it read. Header records are public, write-once accounts. Private consumers read them and never write them, so they do not contend in a block (R11). The consumer owns uniqueness. The reference consumer keys its nullifier on the statement id and its own instance (section 11). A rejected attestation consumes nothing (R2). #### 7. Permissionless operation (F11, F12, R7 to R10)

Anyone can submit a valid update. `Apply` accepts any `Verify` from a verifier listed in the config and checks nothing about the submitter. A test submits an update from a private account created seconds earlier.

| Off-chain participant | Safety or liveness | Why it cannot block |
|---|---|---|
| Update submitter | Liveness only | Any other party submits the same update. A stalled instance resumes by submitting the outstanding updates in order |
| Beacon API provider | Liveness only | The follower fails over across providers. A bad update is rejected by the program |
| Execution RPC provider | Liveness only | Another provider serves the same proof. A bad proof is rejected |
| Claimant's prover | Neither | It is the user's own device |

The follower reads the on-chain head, waits an interval derived from `sha256(instance || follower_id || slot)` in 0 to `jitter_max_s` (default 60 s), reads the head again, and submits only if the update is still needed (R9, R10). A duplicate is rejected with E14 (R8). A restarted follower checks its local store against the on-chain commitment and resumes without re-verifying from the checkpoint (R4). The default cadence is one finality update every 6,144 s, and a handoff goes at once. `docs/OPERATOR.md` has the operator journey. No party is obliged to operate. #### 11. Trust assumptions and verification security (S6, VS1 to VS6)

Full text: `docs/TRUST.md`.

- Sync committee. We trust that fewer than 342 of 512 members collude. If an attacker holds a fraction f of the effective stake, the chance of at least 342 of 512 seats in one period is a binomial tail. At f = 0.5 it is 1.2e-14, at 0.6 it is 8.9e-4, at 0.65 it is 0.21 (computed, not measured). The cheaper attack corrupts the keys of 342 known seats in the 27 hours before a period starts, and costs the attacker no stake because the spec has no slashing for sync-committee signing. This is weaker than Ethereum's economic finality. We state it and do not offer a stronger anchor.
- Checkpoint. One trust input, checked by comparing public sources. A wrong one is fixed by a new instance.
- Gloas. The header attests the bid's parent block hash (generalized index 2,856, consensus-specs `c3e16117`). A payload that was withheld cannot reach a finalised header. A gloas record lags by one or more slots.
- Helios quorum finding. Helios `verify_generic_update` does not enforce the two-thirds quorum and treats a zero finalized header as no finality. `lc_verify` therefore checks decode (E01), finalized header present (E02) and participants of at least `max(min_participants, 342)` (E04) before Helios, and that the store moved (E14) after. Tests `vs2b_below_participation` and `vs2c_header_not_finalised`.
- Nullifier keying. The consumer nullifier is `PDA(program, sha256(domain || program_instance || stmt.id))`. Without the instance in the seed, an attacker's instance can accept a fabricated statement with the id of a real transfer and burn it for good.
- Adversarial suite. `vs1_fabricated_chain`, `vs2a_committee_not_handed_off`, `vs2b_below_participation`, `vs2c_header_not_finalised`, `vs2d_tampered_roots`, `vs2e_wrong_chain_id`, `vs2f_predicate_not_covered`. Each asserts an exact error code.
- Immutability (VS3). `lc_verify` is deployed immutable. Verifier ids are part of the config that fixes the instance address. A fix or a new fork means a new instance, and consumers move as in `docs/CONSUMER-PATTERN.md` section 7. The consumer document states that a program holding our program id in mutable state hands control to whoever writes that state.
- Failure modes and consumer exposure (VS4). Caps, a freeze authority, a delay before large releases, an out-of-band check of large amounts. `docs/TRUST.md` section 5.
